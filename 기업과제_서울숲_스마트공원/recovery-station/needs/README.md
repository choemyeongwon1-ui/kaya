# 맞춤형 추천 — 갈 곳 추천·산책 코스 화면 (목표 3)

「서울숲, 머무는 숲」 대시보드에 더한 세 번째 화면입니다. 컨셉은 **개인의 니즈에 따른 공간 추천과 산책 루트 찾기**입니다.

기존 대시보드는 빌드된 파일만 있고 React 소스가 이 폴더에 없어서, 대시보드 본체는 건드리지 않고 **따로 도는 정적 페이지**로 만들었습니다. 기존 대시보드의 자료(`../data/`)와 스타일(`../assets/index-*.css`)을 그대로 읽어 씁니다. 빌드 과정이 없으므로 파일을 고치면 바로 반영됩니다.

## 화면

| 화면 | 주소 | 하는 일 |
|---|---|---|
| 시민 화면 | `needs/` 또는 `needs/#citizen` | 하고 싶은 일·머물 시간·같이 온 사람을 고르면 갈 곳 3곳을 이유(그늘, 화장실 거리, 붐빔, 몇 시까지 머물 수 있는지)와 함께 추천. 가는 길 또는 산책 코스(20·40·60분)를 그늘·쉼터·계단 없음·한산함 조건으로 짜 줌. 서울숲이 맞지 않으면 근처 무료 장소(도서관·주민센터·공원)를 보여 줌. 큰비 때는 유수지·하천구역을 추천과 길 안내에서 피함 |
| 관리자 화면 | `needs/#admin` | 20m 칸마다 앉을 곳·그늘·화장실·붐빔을 견주어 쉬기 어려운 곳과 이유를 지도에 표시. 벤치·그늘·화장실을 어디에 놓으면 가장 많이 줄어드는지 계산하고 CSV·GeoJSON으로 내려받음. **법적 구역** 보기(칸마다 적용 법·관리 주체·설치 절차), 현장 조사 시설 입력, AI 보고·질문 |

시연용 주소 옵션: `?s=heat|dust|rain|cold`(날씨 상황), `?t=3-14`(요일-시각. 0=일 … 6=토). 예: `needs/?t=6-14` 는 토요일 오후 2시.

## 여는 법

- 배포본: `recovery-station/` 폴더째 올리면 `…/recovery-station/needs/` 로 열립니다. 기존 대시보드 위쪽 탭 줄에 「3 맞춤형 추천」이 생깁니다.
- 내 컴퓨터에서: 파일을 더블클릭하면 안 열립니다(모듈과 자료를 불러올 수 없음). `recovery-station` 폴더에서 `python -m http.server 8000` 을 실행하고 `http://localhost:8000/needs/` 로 엽니다.

## 기존 대시보드와의 연결

기존 대시보드에서 바꾼 것은 `recovery-station/index.html` 에 넣은 한 줄뿐입니다. 원래 파일은 `index_수정전.html` 로 남겨 두었습니다.

```html
<script src="./needs/link.js" defer></script>
```

**대시보드를 다시 빌드하면 이 줄이 사라집니다.** React 소스에서 아래처럼 해 주세요.

1. `needs/` 폴더를 프로젝트의 `public/needs/` 에 넣습니다. Vite는 `public/` 을 그대로 복사합니다.
2. 탭 줄 컴포넌트에 링크를 직접 넣고 `link.js` 는 지웁니다. 소스의 `index.html` 에 위 한 줄을 넣어도 됩니다.
   ```jsx
   <a className="tab goal-tab g3" href="./needs/"><span className="tab-n">3</span>맞춤형 추천</a>
   ```
   링크를 직접 넣을 때는 `link.js` 안의 `--goal3` 색과 `.goal-tab.g3 .tab-n` 규칙을 대시보드 CSS에 옮깁니다.
   소개 화면의 목표 3 카드(`#solution .ans` 안 세 번째 `article.ans-card.g3`)와 맨 아래 단추(`.invite-btns`)도 `link.js` 의 `makeCard()`·`makeInvite()` 내용과 `.ans-card.g3` 규칙을 그대로 옮기면 됩니다.
3. 빌드하면 CSS 파일 이름(지금은 `index-5a-PIen-.css`)이 바뀝니다. `needs/index.html` 의 `<link href="../assets/index-….css">` 를 새 이름으로 고칩니다. 고치지 않아도 `base.css` 로 넘어가 화면은 그대로 나오지만, 대시보드 디자인을 바꾼 경우에는 옛 모습으로 남습니다.
4. 이 화면이 읽는 대시보드 자료: `data/park.geojson`, `grid.geojson`, `network.json`, `features.geojson`, `context.geojson`, `hubs.json`, `team.json`, `meta.json`. 이 파일들의 구조를 바꾸면 `js/model.js` 를 맞춰야 합니다.

탭 이름(「맞춤형 추천」, 「목표 3」)은 `link.js` 와 `js/main.js` 에서 바꿉니다. 테마(라이트·다크)는 기존 대시보드와 같은 저장 이름(`sf-theme`)을 써서 함께 바뀝니다.

## 계산 방법

### 갈 곳 추천 (`recommend.js`)

- 거점 14곳마다 점수를 매깁니다. 기본 비중은 하고 싶은 일 35 · 머물 수 있는 시간 20 · 같이 온 사람 15 · 붐빔 12 · 날씨에 맞는 자리 10 · 걷는 거리 8 · 화장실 5 입니다.
- **같이 온 사람**은 서울숲 SNS 연구(김지은 외 2019)의 동반자 분류를 따라 혼자 · 연인 · 친구 · 아이 · 어르신 · 반려견 여섯 가지입니다. 사람마다 비중을 바꿉니다(`config.js` 의 `COMPANY_W`): 혼자는 붐빔, 연인은 날씨에 맞는 자리, 친구는 하고 싶은 일, 아이·어르신은 화장실과 걷는 거리, 반려견은 붐빔과 산책길. 반려견과 함께면 건물 안과 어린이 놀이터는 빼고 사슴우리는 「출입 확인 필요」로 적습니다(가정 · 서울숲 규정 확인 필요).

### 언제 가면 한산할까 (`recommend.js` 의 `quietHours`)

- 앞으로 24시간 중 공원 낮 시간(6~22시)마다 방문 수준(요일·시각 곡선)과 날씨 판정을 함께 봅니다. 방문 수준이 0.45 미만이고 날씨가 정상이면 「한산 · 날씨 좋음」입니다.
- 곡선은 조현민·권태경(2025, 한국조경학회지 53(4))이 서울숲 보행 계수기 3곳으로 본 패턴에 맞췄습니다: 평일 12시·19~20시, 주말 오후 2~3시에 몰리고 토요일 14시가 한 주 최대, 21시 이후 급감, 주말이 평일의 약 1.6배. 그래프 값을 옮긴 것은 아니고 피크 시각과 비율만 맞춘 추정입니다. 서울숲 실시간 인구 기록이 쌓이면 실측으로 바꿉니다.

### 서울숲 소식 (`news.js`)

- 관리자 화면 「서울숲 소식 올리기」에서 정원·프로그램·공지를 올리면 시민 화면 「오늘 서울숲 소식」에 바로 보입니다. 기간이 지난 소식은 숨기고, 같이 온 사람에게 맞는 소식을 위로 올립니다.
- 시연 단계라 소식은 그 브라우저(localStorage)에만 저장됩니다. 실제 운영에서는 서버 한 곳에 저장해야 모든 시민 화면에 보입니다.
- 공공서비스예약 프로그램은 `analysis/08_programs.py` 가 전체 목록(약 2,400건)에서 장소·이름에 「서울숲」이 있거나 서울숲 중심 700m 안인 것만 골라 `data/programs.json` 에 넣습니다. sample 키는 5건만 주므로 일반 인증키가 필요합니다.
- **머물 수 있는 시간**은 운영 시간 → 밤 → 날씨 → 추위 순으로 따져 지금부터 몇 시까지 되는지 셉니다(12시간 앞까지).
- 추천 순서: 지금 조건에 맞는 곳 → 갈 수는 있지만 붐비거나 시간이 짧은 곳 → 3시간 안에 갈 수 있게 되는 곳 → 그보다 뒤에 가능한 곳(밤에는 내일 아침). 사정은 카드에 노란 꼬리표로 적습니다.
- 꼭 맞는 곳이 3곳이 안 되면 근처 무료 장소를 펼쳐 보여 줍니다. 날씨가 나쁘면 실내(도서관·주민센터)를, 붐빌 때는 공원을 먼저 보여 줍니다.

### 길과 산책 코스 (`route.js`)

- 보행망(`network.json`)에서 가장 짧은 길을 찾고, 고른 조건에 따라 구간 비용을 바꿔 다시 찾습니다. 그늘은 칸의 나무 그늘 비율, 한산함은 구간 혼잡 추정값, 계단 없음은 계단 구간 제외, 쉼터는 쉼터 사이가 먼 구간에 쉼터를 끼워 넣는 방식입니다(가장 짧은 길의 1.35배까지만 돌아감).
- 추운 날(체감 12℃ 미만)에는 「그늘」 조건이 「볕 드는 길」로 바뀝니다. 해가 진 뒤에는 꺼집니다.
- 산책 코스는 공원 안에 고루 퍼진 지점 44곳과 쉼터·거점을 한두 곳 거쳐 목표 길이에 가장 가까운 길을 고릅니다. 같은 길을 되짚거나 공원 밖으로 나가는 길은 벌점을 주고, 남으면 화면에 몇 m인지 적습니다.
- 휠체어·유모차를 고르면 계단을 피하고 시속 3.2km로 계산합니다(기본 4.2km).

### 쉬기 어려운 곳 (`rest.js`)

- 팀 20m 격자 1,003칸(40.1ha, 보류 94칸 제외)마다 네 가지를 봅니다.

  | 항목 | 일반 이용자 | 어르신·유아 |
  |---|---|---|
  | 앉을 곳까지 걷는 거리 | 150m 안 | 100m 안 |
  | 화장실까지 걷는 거리 | 250m 안 | 150m 안 |
  | 나무 그늘 | 30% 이상 | 50% 이상 |
  | 붐빔 지수 | 60 미만 | 50 미만 |

- 두 가지 이상 어긋나면 「쉬기 어려운 곳」입니다. 붙어 있는 칸은 구역으로 묶어 넓이와 이용 정도 순으로 세웁니다.
- 시설 자리는 「놓았을 때 기준 안으로 들어오는 칸이 가장 많은 길 위 지점」을 하나씩 고르는 방식입니다. 그늘은 그늘이 모자라고 사람이 많이 지나는 길가를 고르고, 팀이 앞서 정한 식재 후보 칸과 겹치면 표시합니다.

### 법적 구역 (`data/legal.json`)

브이월드 연속지적도에서 공원 경계 안 필지 151개(50㎡ 이상)를 뽑고, 필지마다 토지이음 토지이용계획을 조회해 지정을 붙였습니다(2026-11-16 조회). 칸과 거점은 가장 넓게 겹치는 필지의 지정을 따릅니다.

| 구역 | 넓이(공원 경계 안) | 어디 | 시설을 놓을 때 |
|---|---|---|---|
| 공원 | 35.1만㎡ (53%) | 가족마당·거울연못·방문자센터 등 가운데 | 공원시설 기준 |
| 공원 + 하천구역 | 11.9만㎡ (18%) | 남쪽 강변 띠(중랑천·한강 쪽), 수도박물관 | 하천점용허가 필요 |
| 공원 + 정수장 부지 | 9.0만㎡ (14%) | 곤충식물원·나비정원 쪽(지목 수도용지) | 상수도사업본부와 협의 |
| 유수지 | 5.3만㎡ (8%) | 습지생태원, 복합문화센터 부지 | 빗물을 담는 기능이 우선 |

- **시민 화면**: 큰비(호우 경고, 시간당 15mm 이상) 때와 그친 뒤 3시간 동안은 유수지·하천구역의 야외 자리를 추천하지 않고, 카드에 「큰비로 물이 차는 구역」이라고 적습니다. 길 찾기도 그 구역을 지나는 구간에 4배 벌점을 줘 되도록 피하고, 지나야 하면 몇 m인지 적습니다. 실내 시설(수도박물관·복합문화센터)은 그대로 추천합니다.
- **관리자 화면**: 지도의 「법적 구역」 보기에서 칸을 구역 색으로 칠하고(격자 밖 습지생태원도 경계로 표시), 칸을 누르면 적용 법·관리 주체·설치 절차를 보여 줍니다. 시설 제안 자리마다 구역을 붙이고, 공원 단독 구역이 아닌 자리는 허가·협의가 필요하다고 따로 알립니다. CSV·GeoJSON과 AI 자료에도 `법적구역·관리·설치절차`가 들어갑니다.
- 값(큰비 뒤 피하는 시간, 길 벌점, 구역 색)은 `js/config.js` 의 `FLOOD_AFTER`, `FLOOD_PENALTY`, `LEGAL_COLOR` 에 있습니다.

## 기존 대시보드와 다른 규칙 (이 화면에서 더한 가정)

날씨 단계 기준, 붐빔 추정식, 걷는 속도, 계단 벌점은 기존 대시보드와 같습니다. 아래는 이 화면에서 새로 정한 것이고, 값은 모두 `js/config.js` 에 있습니다.

- **운영 시간**: 곤충식물원·나비정원은 공식 자료로 확인했습니다. 수도박물관·복합문화체육센터·방문자센터·수변휴게실은 확인하지 못해 보수적으로 잡았고 화면에 「운영시간 확인 필요」로 적습니다.
- **밤**: 22시~6시에는 야외 자리를 추천하지 않습니다.
- **추위**: 체감 0℃ 미만이면 야외에 오래 머물기 어렵다고 봅니다(걷기·운동·놀이는 −8℃).
- **비**: 비가 오면 그늘 자리도 머물기 어렵다고 봅니다. 기존 대시보드는 그늘 자리를 비 올 때도 괜찮다고 봅니다.
- **붐빔**: 기존 대시보드는 수용의 85%를 넘으면 머물 수 없는 곳으로 치지만, 여기서는 머물 수 있는 시간과 따로 보여 주고 순서만 뒤로 미룹니다.
- **한파 상황**을 시연용 날씨에 더했습니다.
- **실내 시설의 화장실**: 방문자센터·수변휴게실·복합문화체육센터·수도박물관은 건물 안에 화장실이 있다고 가정했습니다.
- **출발점**: 「서울숲역 방면 입구」 좌표가 광장과 이어지지 않은 골목 끝에 붙어 1.7km를 돌아가는 문제가 있어, 150m 안의 공원 안 길에 붙이도록 했습니다. 기존 대시보드의 길 찾기에도 같은 문제가 있습니다.
- **장소별 적합도**(어떤 곳이 어떤 일에 맞는지)는 팀이 정한 가정값입니다. 설문 결과가 나오면 `AFFINITY` 표를 바꿉니다.

## 서울숲 실시간 붐빔 (코스 찾기 화면)

- 자료: 서울 열린데이터광장 「서울시 실시간 도시데이터 — 인구」(OA-21778, `citydata_ppltn`), 장소 '서울숲공원'(POI101). 통신사 기지국 신호로 어림한 값이고 5분마다 바뀜.
- 길: 화면 → Supabase 중계 서버(`proxy/seoul-crowd`, 'kaya' 프로젝트) → 서울시. 서울시 주소가 http 전용·CORS 없음이라 바로 못 부름. 인증키는 Supabase 비밀 보관함(Vault)에만 있고 코드·저장소에는 없음.
- 화면: 위쪽 배지(누르면 자세히), 첫 단계의 「지금 서울숲」 카드 — 붐빔 4단계(여유·보통·약간 붐빔·붐빔), 인원 범위, 앞으로 8시간 예보 막대, 6~22시 중 가장 한산한 때.
- 가늠 문구 「축구장 한 면 넓이에 약 N명꼴」 = 인원 ÷ 서울숲 면적(주제서 기준 약 49만㎡) × 축구장 한 면(105×68m = 7,140㎡). 서울시 '서울숲공원' 집계 구역이 공원 경계와 같은지는 (검증 필요)라 어림값으로만 표시.
- '약간 붐빔' 이상이면 누구와 왔든 한산한 길로 코스를 짬. 응답이 없으면 배지·카드를 숨기고 요일·시간대 추정만 씀.

- 화면: 첫 단계의 「서울숲 날씨」 카드 — 지금(기온·체감·습도·바람) + 오늘·내일·모레·글피(최고/최저, 강수확률, 최대 풍속, 평균 습도) + 한 줄(비 소식 60% 이상 또는 강풍 9m/s 이상). 시연 날씨(`?wx=`)일 땐 숨김.
- 고친 것: Open-Meteo 바람이 km/h로 오고 있어 `wind_speed_unit=ms`로 맞춤.

## 왜 서울숲인가 — 이용자 화면에 담은 방식

팀 논리(일터 옆 숲 · 무료로 머무는 곳 · 실제 혼잡 · 시민 참여 · 물·숲·습지 · 폭염 피난처)를 설명문으로 늘어놓지 않고, **지금 상황에 맞는 이유 하나**만 보여 줍니다(`tour.js` `situation`·`statusBar`·`quickBlock`).

### 첫 화면 구성 (2026-11-20 간소화)

예전 첫 화면은 인사 카드 → 붐빔 카드 → 날씨 카드(4일) → 질문 → 추천 코스 4개 → 프로그램 순으로, 휴대폰에서 화면 2.7배 길이(1488px)라 정작 질문이 세 번째 화면에 나왔음. 지금은 **고르는 것 먼저, 정보는 한 줄로**(746px, 질문·고르기·바로 출발이 첫 화면 안에 보임).

1. **지금 상태 한 줄** — 기온(체감) · 미세먼지 등급(PM10·PM2.5 중 나쁜 쪽) · 붐빔 단계. 누르면 예전 붐빔·날씨 카드가 그대로 펼쳐짐(자료·출처 유지).
   평소엔 한 줄만, 아래 표의 상황일 때만 색 띠와 한 문장이 붙음(위험할 때만 눈에 띄게).
2. **무엇을 하고 싶나요?** — 6개를 3열로(타일 높이 절반).
3. **고르기 어렵다면, 바로 출발** — 상황 맞춤 코스(퇴근길) + 추천 코스, 합쳐 2개만. 나머지는 「추천 코스 N개 더 보기」.
4. **이번 주 서울숲 프로그램** — 가장 가까운 1개만, 나머지와 설명은 「더 보기」.

| 상황 (우선순위 순) | 화면 | 근거 |
|---|---|---|
| 체감 31℃ 이상 낮 | 상태 줄 노란 띠: 「더운 날이에요. 서울숲 안은 바깥 거리보다 5.5~7.4℃ 낮았어요…」 | 조현민·권태경(2022) 서울숲 실측(지점 1곳씩 비교) |

- 컨셉 「한 곳씩 들러 보고, 좋으면 그대로 · 별로면 바로 다른 곳으로」: 출발 전 코스 화면에 표정 2개와 함께 안내하고, 도착 평가 화면에도 「좋으면 그대로 가고, 별로면 남은 코스를 바로 바꿔요」로 같은 말을 씀.
- 평가 화면(이전 문구: 「남겨 주신 의견으로 남은 코스를 바로 고쳐요」)(팀 논리 4 — 이용자 의견으로 운영). 표정은 익명 합계로 서버에 모이지만 다른 사람의 코스를 바로 바꾸지는 않으므로 "다른 사람 코스가 바뀐다"고는 쓰지 않음.
- 마침 화면의 「돈 들이지 않고 숲에서 약 N분 머물렀어요」는 노골적이라 뺌(2026-11-19). 팀 논리 2(무료로 머무는 숲)는 화면에 대놓고 쓰지 않고 첫 화면 문구 정도로만 둠.
- 공원 밖(위치 없음)에서 출발하면: 예전엔 점이 길을 따라 한 구간 5~14초씩 걸어가는 재생이 있었으나 느리고 목적이 불분명해 뺌. 지금은 길만 그리고 「도착 화면 보기」 단추로 바로 넘어감. 공원 안에서는 기존처럼 내 위치를 따라 저절로 도착.
- 마무리 흐름(2026-11-20 고침): 예전엔 마지막 곳을 평가하면 지도가 전체 코스로 다시 날아가며 점선이 흐르고, 가장 큰 단추가 「이 코스로 바로 걷기」라 '다시 재생'처럼 느껴졌음. 지금은
  **오늘 산책, 여기까지예요(걸은 길 조용히 표시) → 코스 흐름 표정 → 「나가는 길 안내받기」(가장 가까운 출구까지 노란 길 · 화장실) → 「다 나왔어요」 → 작별 화면(오늘 걸은 곳·시간, 다음에 오기 좋은 때) → 처음 화면으로**.
  '다음에 올 때는' 코스는 보조 상자로 내리고, 더 걷고 싶은 사람만 작은 글자 단추로 이어 걷기.
- 화면에 쓰지 않은 것: 연혁(경마장·골프장·시민 모금)과 "유일한 공원" 같은 비교 주장 — 출처 확인 전(검증 필요).

## 도착 평가: 표정 3개 1탭 (코스 찾기)

- 방식: 거점 25m 안에 들어오면 위치로 도착을 알아채고(기존), 그 자리에서 **「이 자리, 쾌적한가요?」 + 표정 3개(좋아요·보통·별로)** 하나만 누르게 함. 글 입력 없이 1초.
- 동작: 좋아요 → 좋았던 점 칩 + 2.2초 뒤 저절로 다음 곳, 보통 → 아쉬운 점 칩 + 3.5초 뒤 다음 곳(남은 코스를 약하게 다시 짬), 별로 → 까닭 칩(붐빔·거리·볼거리·더위추위·쉴 곳화장실)을 고를 때까지 기다리고 남은 코스를 다시 짬.
- 저장: 기존 별점과 같은 모양으로 좋아요=5·보통=3·별로=1점(`review.js` `FACES`). 마침 화면은 '좋았던 곳 N/M곳', 장소 제목 옆은 다른 이용자 '좋아요 N%'.
- 얼굴은 기기마다 달라지는 이모지 대신 직접 그린 그림(`review.js` `FACE_SVG`), 색은 좋아요 민트·보통 노랑·별로 분홍.
- 서버 저장(익명, 2026-11-19 추가): 표정을 누르고 다음 곳으로 넘어가거나 산책을 마치면 한 건을 `proxy/comfort`(Supabase Edge Function)로 보냄.
  - 보내는 것: 거점 id · 표정(5/3/1) · 고른 까닭 칩 · 그때 체감온도 · 초미세먼지 · 실시간 붐빔 단계(0~3) · 동행 유형. 날짜·시각은 서버가 서울 시각으로 붙임.
  - 저장하지 않는 것: 이름·기기 정보·좌표·IP·자유 의견 글(의견 글은 기기에만 남음). 화면에도 「표정은 이름·위치 없이 공원 개선 통계에만 쓰여요」라고 적음.
  - 쏠림 방지: 같은 기기에서 같은 곳은 30분에 한 번만 보냄(`sf-comfort-sent`), 서버는 같은 접속지 10분 30건까지(메모리에서만 셈). 시연 날씨(`?s=`)로 본 산책은 보내지 않음.
  - 표 `public.comfort_votes`는 RLS를 켜고 anon·authenticated 권한을 모두 뺐음 → 브라우저에서 직접 읽거나 쓸 수 없고, 서버만 씀. GET은 합계만 돌려주고 개별 응답은 내보내지 않음.
- 관리자 화면 「4 방문자 쾌적함」(`admin.js` `renderComfort`): 기간(7·30·90일·1년)별
  - 거점별 좋아요 비율(낮은 곳부터)과 많이 꼽힌 아쉬움(붐빔·더위·쉴 곳 부족 등) → 그늘시설·쉼터·동선 보완 후보
  - 거점 × 시간대(오전·점심·오후·저녁·밤) 좋아요 비율 — 낮은 칸이 진하게
  - 상황별 비교: 체감 31℃ 이상 vs 그 밖, 초미세먼지 36㎍/㎥ 이상 vs 그 밖, 붐빔(2단계 이상) vs 여유 — 차이를 %p로. 기준값은 주제서 예시값(31℃·36)을 그대로 씀
  - 응답 5건 미만 칸은 흐리게 '표본 적음'. 통계 검정(예: 비율 차 검정)은 응답이 쌓인 뒤 추가할 것

## 이 코스를 고른 기준 (코스 화면, 2026-11-20)

추천 경로를 주는 서비스라면 기준을 밝혀야 한다는 피드백으로 추가. 코스 화면 「이 코스를 고른 기준」을 펼치면(`tour.js` `criteriaBox`):

1. **장소**: 7가지 점수(하고 싶은 일 · 머물 시간 · 같이 온 사람 · 붐빔 · 더위추위 · 걷는 거리 · 화장실)의 **이번 코스 실제 비중**(동행 유형·남긴 의견 반영 뒤 %)과, 들르는 곳마다 실제 값(적합도 · 붐빔 수용률 · 화장실 거리 · 머물 수 있는 시각). 이용자 평가 반영 건수(시연용 가상 평가 포함 여부 표시).
2. **길**: 고른 길과 가장 짧은 길의 거리 비교, 그늘진 길 %, 계단 수, 흙길·자갈길 m, 상가 맞닿은 길 m. 돌아가는 상한(그늘·한산 1.2배, 쉼터 1.35배)과 순서 정하는 방법(가능한 순서 전부 비교).
3. **쓴 자료와 기준 시각**: 붐빔(서울시 실시간 도시데이터 hh:mm 또는 추정), 날씨(기상청 발표 시각 등 `app.wx.source` 그대로), 길·상가(OSM)·그늘(팀 20m 격자).
4. **기준값과 근거**: 기준마다 값 · 출처 · 성격 꼬리표 — `공식 기준`(환경부 대기질 등급, 기상청 폭염주의보 33℃), `측정 자료`(서울시 실시간·서울숲 실측·OSM), `연구 근거`(논문), `연구 + 팀 값`, `팀이 정한 값`(점수 비중 등).
   - 객관성 원칙: 측정·공식·연구에서 온 값과 **팀이 정한 값(가정)을 나눠 그대로 보여 줌**. 가정 값은 현장 설문·이용자 평가가 쌓이면 바꾼다고 명시.
   - 폭염주의보: 일 최고 체감온도 33℃ 이상이 2일 이상 이어질 것으로 예상될 때(기상청, [폭염 안전 가이드](https://www.weather.go.kr/w/hazard/heatwave/safety-guide.do), 2026-11-20 확인). 31℃는 주제서 예시값.

## 구간 속성: 포장 상태 · 상권 인접 (2026-11-20)

- 만드는 법: `python needs/tools/edge_extras.py` → `needs/data/edges_extra.json`(보행망 구간 1,191개와 같은 순서). 없으면 화면은 그대로 열리고 이 두 조건만 빠짐.
- **포장 상태**: OpenStreetMap 길의 `surface` 태그(Overpass API, 2026-11-20 받음, ODbL). 구간 1/4·1/2·3/4 지점에서 12m 안의 태그 있는 길을 다수결 → 0 모름 · 1 포장(아스팔트·콘크리트·보도블록·데크) · 2 비포장(흙·자갈·잔디·황토).
  - 길찾기: 계단 없는 길을 고르는 경우(아이·어르신 동행)에 비포장 구간 비용을 올림. 코스 화면에 가장 짧은 길보다 실제로 30m 이상 덜 지날 때만 「흙길·자갈길을 피해 포장길로 · 비포장 ○m → ○m」.
  - **한계**: 공원 안 보행망 17.6km 가운데 태그가 있는 건 4.6km(포장 2.5km · 비포장 2.1km)뿐, 나머지 약 74%는 '모름'(벌점 없음). 현장 조사나 서울시 공원 시설 자료로 채워야 정확해짐.
- **상권 인접**: `data/shops.json`(OSM 상점·음식점·카페 1,146곳, 2026-11-15)에서 구간 중간점 60m 안 개수. 8곳 이상이면 최대치.
  - 길찾기: 한산한 길을 고르는 경우(혼자·반려견·붐빔 의견·실시간 약간 붐빔 이상)에 상권 맞닿은 구간 비용을 올림. 실제로 30m 이상 덜 지나면 「성수동 상가 쪽 번잡한 길을 피했어요」.
  - 분포: 상점 3곳 이상 맞닿은 구간은 공원 밖 거리 2,974m · 공원 안 246m(성수동 쪽 가장자리) → 주로 공원 밖에서 걸어 들어오는 길과 가장자리 길에 영향.

## 산책 마무리 (마침 화면, 2026-11-20)

예전엔 숫자 세 개(걸은 시간·거리·좋았던 곳)로 뚝 끝났음. 지금은 아래 순서로 이어짐.

1. **오늘 걸은 길**: 지도에 걸은 길 전체, 들른 곳 핀마다 누른 표정. 패널엔 들른 순서와 표정·까닭.
2. **코스 전체 한 번 묻기**: 「오늘 코스, 이어지는 흐름은 어땠어요?」 표정 3개 + 칩
   - 좋음: 동선이 자연스러웠어요 · 볼거리가 다양했어요 · 쉬며 걷기 좋았어요
   - 아쉬움: 되돌아가는 길이 많았어요 · 중간에 쉴 곳이 없었어요 · 비슷한 곳만 이어졌어요 · 너무 길었어요 · 너무 짧았어요
   - 익명으로 `proxy/comfort`에 `{kind:'course'}` 한 건(표 `public.course_votes`): 표정 · 칩 · **들른 곳 순서** · 추천 코스 id · 활동·동행·머문 시간 · 걸은 분·m · 체감온도·초미세먼지·붐빔. 같은 산책은 한 번만, 표정을 누르고 6초 뒤(또는 화면을 떠날 때) 보냄. 시연 날씨면 안 보냄.
3. **다음엔 이런 코스**: 같은 조건으로, 오늘 들른 곳은 빼고 좋았던 곳과 비슷한 결의 코스를 미리 보여 줌. 코스 평가가 바로 반영됨(너무 김 → 한 곳 줄임, 너무 짧음 → 한 곳 늘림, 쉴 곳 없음 → 쉼터·화장실 가까운 길, 비슷한 곳만 → 장소정체성 높은 곳 우선). 「이 코스로 바로 걷기」로 이어 걷기. 오기 좋은 때(한산·날씨)도 함께.
4. **나가는 길**: 마지막 곳에서 보행망으로 가장 가까운 출입구(서울숲역 방면·북쪽)까지 거리·분, 가까운 화장실 거리. 「길 보기」를 누르면 지도에 노란 점선.

관리자 화면 「4 방문자 쾌적함」 아래 **코스 흐름**: 코스 응답 수·좋아요 비율, 까닭 순위(좋음 초록·아쉬움 주황), **구간별**(이어서 걸은 두 곳) 좋아요 비율과 많이 꼽힌 아쉬움 — 낮은 구간부터, 머문 시간별·추천 코스별 비교. 구간 집계는 코스 전체 답을 그 코스의 모든 구간에 똑같이 나눠 세는 방식이라, 어느 구간 탓인지는 응답이 쌓여 겹치는 구간끼리 비교해야 드러남.

## 근거 논문 (코스 찾기 화면 `tour.html` 에 반영한 것)

- 나무 그늘은 여름 위성 영상 기준이라 겨울에는 다릅니다.
- **습지생태원 구역(도로 건너 북쪽)은 팀 20m 격자 밖입니다.** 그래서 「쉬기 어려운 곳」 판정과 시설 제안에서 빠져 있고, 습지생태원은 추천 카드에 그늘 비율 대신 「그늘 자리 · 분석 범위 밖이라 그늘 비율은 모름」으로 나옵니다. 그쪽으로 가는 길의 그늘 비율도 격자 안 구간만으로 셉니다.
- **법적 구역**은 토지이음 열람 정보 기준이며 법적 효력이 없습니다. 실제 설치 전에는 토지이용계획확인서로 확인해야 합니다. 50㎡ 미만 조각 필지는 뺐고, 공원 경계는 OpenStreetMap 기준입니다. 「큰비 때 물이 차는 구역」은 법적 지정(유수지·하천구역)으로 어림한 것이고 실제 침수 기록은 아닙니다.
- 근처 무료 장소는 OpenStreetMap 기준이라 빠진 곳이 있을 수 있고, 운영 시간은 종류별 어림값입니다(주민센터 평일 9~18시, 도서관 9~18시). 성수도서관은 서울시 미디어허브 기사로 위치를 확인했습니다.
- 날씨는 Open-Meteo 예보·대기질 모델값입니다. 연결이 안 되면 표본 날씨로 바뀌고 화면 아래에 그렇게 적힙니다. 시연용 시각을 고르면 실제 예보 대신 표본 날씨를 씁니다.
- 지도와 시설: © OpenStreetMap 기여자 (ODbL).

`data/` 를 다시 만들려면 프로젝트 폴더에서 `python -I analysis/06_needs.py .` 을 실행합니다.

## AI

관리자 화면의 「AI에게 맡기기」는 Claude가 진단 결과를 읽고 관리자용 보고를 쓰거나 질문에 답하는 기능입니다. AI 없이도 계산으로 뽑은 요약은 항상 보입니다.

- 모델: `claude-opus-5-5` (`js/config.js` 의 `AI.model`). 공식 Anthropic SDK(`@anthropic-ai/sdk` 1.8.0)로 부르고, 답은 오는 대로 화면에 이어 붙입니다.
- **API 키는 쓰는 사람이 직접 넣습니다.** 키는 그 브라우저에만 저장되고(기본은 탭을 닫으면 지워짐) Anthropic API로만 보냅니다. 요금은 키 주인 계정에 붙습니다.
- 보내는 것: 진단 집계값, 구역·제안 자리의 장소 이름, 질문. 화면의 「AI에 보내는 자료 보기」에서 그대로 확인할 수 있습니다. 개인정보는 없습니다.
- 모델이 답을 거절하면 Anthropic이 정한 다른 모델이 이어서 답하도록 하는 설정(server-side fallback)을 켜 두었습니다. 그렇게 답한 경우 화면에 적힙니다.
- 브라우저에 키를 넣는 방식은 시연과 내부 사용에만 맞습니다. 누구나 쓰는 서비스로 열려면 키를 서버에 두고(예: Supabase Edge Function) 그 서버를 거쳐 부르도록 `js/ai.js` 를 바꿔야 합니다.
- 실제 키로 호출해 보지는 못했습니다. 요청 형식, 오류 안내(키 없음·잘못된 키·모델 없음·거절), 답 표시는 모의 응답으로 확인했습니다.

SDK 묶음 파일을 다시 만들려면:

```
npm i @anthropic-ai/sdk esbuild
echo "import Anthropic from '@anthropic-ai/sdk'; export default Anthropic;" > entry.mjs
npx esbuild entry.mjs --bundle --format=esm --platform=browser --target=es2022 --minify --legal-comments=none --outfile=vendor/anthropic-sdk.mjs
```

## 소개 첫 화면 3D 점구름 지도 (`hero3d.js`)

소개 첫 화면 오른쪽 지도 자리에 서울숲·성수 일대를 3D 점구름으로 그립니다. 서울숲에서 시작해 바깥으로 퍼지며, 건물이 바닥에서부터 점으로 쌓여 올라옵니다.

- 원래 Leaflet 지도는 지우지 않고 숨깁니다. 오른쪽 위 「2D 지도」 단추로 되돌아가고(거점별 혼잡 점은 2D 지도에만 있습니다), 고른 값은 탭을 닫을 때까지 기억합니다.
- 자료: `data/city3d.json` — OpenStreetMap 건물 1,802동과 `basemap.json`·`park.geojson` 의 도로·철도·물길·공원 경계. `python analysis/11_city3d.py` 로 다시 만듭니다(인증키 필요 없음).
- **건물 높이는 일부만 실제 값입니다.** 높이·층수 정보가 있는 543동만 그 값을 쓰고, 나머지는 바닥 면적으로 추정했습니다. 화면에 「건물 높이 일부 추정」이라고 적습니다.
- 서울숲 나무 점의 색과 왼쪽 아래 「서울숲 지금」은 서울시 실시간 혼잡도(공원 전체 한 값)를 따릅니다. `live.js` 와 같은 순서로 읽습니다(실시간 중계 → `data/live/latest.json`).
- 외부 라이브러리 없이 WebGL만 씁니다. WebGL을 못 쓰는 기기에서는 원래 2D 지도가 그대로 보입니다. 「움직임 줄이기」 설정이면 나타나는 효과와 회전을 건너뜁니다.
- 확인용: 주소에 `?c3t=8` 을 붙이면 다 나타난 장면부터 봅니다.
- 다시 빌드할 때: `index.html` 의 `<script src="./needs/hero3d.js?v=…" defer>` 줄이 지워지므로 다시 넣습니다. 되돌리려면 이 줄만 빼면 됩니다.
